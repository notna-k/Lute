# Implementation Plan: Worker Labels & Job Routing

**Branch**: `001-worker-labels-routing` | **Date**: 2026-05-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/001-worker-labels-routing/spec.md`

## Summary

Add a key-value label system to workers and an optional selector field on jobs so that the
dispatcher routes jobs only to workers whose label set is a superset of the job's selector.
The change touches the data model (Worker + Job), the gRPC dispatch path
(`ConnectionManager.FindAvailableWorker`), the REST API (label CRUD + enqueue selector), the
proto contract (`WorkerRegistration`), and the React UI (label editor + filter).

## Technical Context

**Language/Version**: Go 1.26 (api, worker), TypeScript / React 18 (ui)

**Primary Dependencies**: Gin, GORM (SQLite dev / PostgreSQL prod), golang-jwt/jwt v5,
google.golang.org/grpc, @tanstack/react-query, TailwindCSS

**Storage**: `workers` table gains a `labels` JSON column. `queue_slots.payload` JSON gains a
`selector` field (no DDL change needed — existing rows deserialise selector as nil).

**Testing**: `go test ./...` per module; `npm run lint` for ui; `make go-lint` before PR.

**Target Platform**: Linux server (api + worker binary), browser (ui SPA embedded in api binary)

**Project Type**: Web service (api) + CLI daemon (worker) + SPA (ui)

**Performance Goals**: Label matching adds < 1 µs per dispatch cycle (in-memory map lookup).
No measurable latency increase visible to end users.

**Constraints**: Backward compatible — jobs without selector and workers without labels continue
to work identically. Proto change is additive (new optional field).

**Scale/Scope**: Up to 500 workers per user, 32 labels per worker, 32 selector pairs per job.
