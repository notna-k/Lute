---
title: "Authentication"
description: "Create and use an API key to talk to the public Lute API."
---

The public Lute API uses a single authentication scheme: a **bearer token**
issued from the Lute dashboard. The same token works for every endpoint under
`/api/public/v1`. The Lute UI itself uses a separate, session-based auth flow
and is not part of the public API.

## Create an API key

You issue API keys from the Lute UI (Settings → API keys) or programmatically
through the authenticated internal endpoints used by the UI.

When a key is created, the full token is returned **exactly once**. Lute
never stores the plaintext token — only a short public prefix for lookup and
a SHA-256 hash for verification. Store the token in a secret manager
immediately; if you lose it, issue a new key.

A token looks like this:

```
lute_sk_xxxxxxxxxxxxxxxxxxxxxxxx
```

The first eleven characters (`lute_sk_` plus eight) are the public prefix
shown in the dashboard. Everything after is the secret portion.

## Send the token

Add the token as a standard `Authorization: Bearer` header on every request.

```bash
curl https://api.lute.app/api/public/v1/runs \
  -H "Authorization: Bearer lute_sk_xxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"queue":"default","type":"container","payload":{}}'
```

## Rotate and revoke

Rotate keys whenever a teammate leaves or a secret may be exposed. Revocation
is immediate: the next request with the revoked key receives `401` with error
code `unauthorized`.

## What your key can do

Every API key is bound to the user account that created it and can:

- create, list, inspect, retry, and cancel runs owned by that user,
- read the job logs of those runs,
- receive webhook events for those runs.

Keys cannot read other users' data. They cannot manage workers or the UI
dashboard — those operations require a browser session with your identity
provider.
