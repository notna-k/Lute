---
title: "Errors"
description: "Response envelope and how to handle each status code."
---

Every error response from the public API uses the same JSON envelope:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "webhook.url is required when webhook is provided"
  }
}
```

`code` is a stable machine-readable identifier; `message` is meant for
humans and may change over time.

## Status codes

| HTTP status | `code`            | Meaning                                                      |
|-------------|-------------------|--------------------------------------------------------------|
| 400         | `invalid_request` | The request body or query string is malformed.               |
| 401         | `unauthorized`    | Missing or invalid API key.                                  |
| 404         | `not_found`       | No resource the API key owns matches the id.                 |
| 409         | `invalid_state`   | The resource exists but is not in a state that allows this operation (e.g. cancelling a running run). |
| 429         | `rate_limited`    | Too many requests in a short window. Retry with backoff.     |
| 500         | `internal_error`  | Unexpected server error; safe to retry with backoff.         |
| 502 / 503   | `bad_gateway`, `unavailable` | A downstream dependency (worker, queue) is temporarily unavailable. Retry. |

## Retry guidance

- **Never** retry `400` or `404` — the request itself is the problem. Fix
  inputs and resubmit.
- **Always safe** to retry `408`, `425`, `429`, `500`, `502`, `503`, and
  `504` with exponential backoff and a reasonable cap (for example, six
  attempts doubling from one second).
- When retrying `POST /runs`, send the same `idempotency_key` to avoid
  creating a duplicate run.

## Correlation

Every response carries a `Request-Id` response header. Include it in bug
reports or support requests — it is how Lute correlates your request with
internal logs.
