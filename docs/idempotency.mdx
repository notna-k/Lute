---
title: "Idempotency"
description: "Safely retry create-run calls after network failures."
---

Every `POST /runs` accepts an optional `idempotency_key` string. Lute stores
a unique index on `(user_id, idempotency_key)`, so a second request with the
same key returns the existing run instead of creating a new one.

## When to use it

Use an idempotency key whenever your caller can retry a request and you do
not want a second execution if the first one actually succeeded but the
network swallowed the response.

Typical keys:

- `daily-<YYYY-MM-DD>` for once-a-day jobs.
- `<your-system-job-id>` for a 1:1 mapping to your internal record.
- A UUID your service generates when it first queues the work.

## Semantics

- First request: creates the run, returns `201 Created`.
- Subsequent requests with the same key and payload: returns `200 OK` with
  the original run. The payload is not re-validated; whatever you originally
  sent is what Lute runs.
- Keys are scoped to the API key's owner; different users never collide.
- Keys never expire automatically. Use monotonic or time-bucketed keys if
  you want to recycle names safely.

## Example

```bash
curl https://api.lute.app/api/public/v1/runs \
  -H "Authorization: Bearer $LUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "queue": "default",
    "type": "container",
    "payload": {"runtime": "alpine:3.19", "command": "echo hi"},
    "idempotency_key": "deploy-abcd1234"
  }'
```

Retrying the same request after a timeout is safe: you will get the same
`id` back and no duplicate run will execute.
